## 비교에 따른 수신 방향 — 소스·독립 리뷰, 실응답 미검증

**Genuine page-owned SDK send·인증·활성화된 보호·정상 request serialization은 유지하고, 수신 성공 증거를 요청에 묶인 raw final·정상 stream completion·동일 context의 SId 성공 action·정확한 동일 CID 서버 history에 둡니다.** 비교한 프로젝트에서 깊은 private Angular/Rx service coupling은 찾지 못했지만, 이 제한된 조사로 모든 외부 프로젝트의 부재를 주장하지 않습니다. HTTP 구현이 짧다는 이유만으로 현재 계정의 보호·모델·파일·완료 계약을 충족한다고 판단하지도 않습니다.

새 빈 background home의 고정 텍스트 시험에서는 original request-owned `Oub` full final TURN 또는 source terminal marker, 원래 observable의 정상 completion, 같은 context의 SId 성공, strict same-CID raw history를 받도록 구현했습니다. Marker-only는 보이지 않은 live 필드를 추정하지 않으며 full receipt의 비교는 유지합니다. Source continuation은 새 생성이 아니라 정보를 보관하는 action에만 대응하고, 그 정보만으로 완료 처리하지 않습니다. 소스 조사와 독립 리뷰에 따라 `IId/ka/Qe/Ne` 표시 tuple의 긍정 copy-equality만 제거했고 **SDK의 negative/terminal/context 관측은 유지했습니다.** 합성 회귀는 통과했으나 설치된 실계정 응답은 미검증입니다. Downstream reducer/effect 오류가 정상 completion처럼 흡수될 수 있다면 필요한 오류 관측은 UI 복사본 동일성과 별개로 유지해야 합니다.

후보의 필수 조건은 다음과 같습니다.

- 승인된 실제 packet·원래 SDK 인자·계정 모델 receipt·source/초기 빈 상태·문서/operation 소유권과 physical 한 번 전송 경계를 유지합니다. 보호 값의 생략·추론·조작, 쿠키/토큰의 확장·서버·저장소·로그 이동, paid API fallback을 허용하지 않습니다.
- Final receipt를 하나의 captured request와 그 원래 stream에 묶습니다. Explicit final·선택 candidate·완료·non-stopped·지원하는 text representation을 확인하고 DTO는 그대로 전달합니다. 첫 owned final에서 생성 허가를 영구히 닫으며 종료·history·teardown을 거쳐 다시 열지 않습니다.
- 최종 문자열이나 stream EOF만으로 성공을 인정하지 않습니다. 원래 stream의 성공 completion 뒤, 정상 SDK로 captured CID만 읽어 exact prompt/lineage·RID·선택 candidate·승인 모델·explicit final/non-stopped completion·bounded saved turn·정확한 답변을 증명해야 합니다. 알려진 stop/error·취소·lease 상실·변경된 context는 계속 terminal이며 uncertain 요청을 재생성하지 않습니다.
- History await 전후와 retirement 직전에 실제 소유권·취소·writable target을 다시 확인합니다. UI store를 긍정 성공 증거에서 제외하더라도 그 store의 대화 ID를 무검증 삭제 대상으로 사용할 수 없습니다.
- 고정 시험의 단순화를 임의 원본·첨부·메인 반환으로 확대하지 않습니다. 이후 문맥/파일 경로는 승인한 전체 scope와 원본·업로드 receipt·same-conversation history membership을 별도로 입증해야 합니다. Partial 답변·잘림·unknown rich output·첨부 누락을 조용히 성공으로 처리하지 않습니다.

공개 소스 확인은 서비스 허용·현재 계정 생성 성공·안전한 서버 취소·스토어 승인 증거가 아닙니다. 실제 결과·실행 여부·실패 원인·현재 구현 상태는 [검증 기록](../testing/validation.md)과 [백그라운드 전송 조사](background-web-transport.md)를 확인하며 이 비교에 중복 기록하지 않습니다.

현재 genuine page SDK는 실제 계정의 정상 보호·직렬화 경로를 유지하면서 검토한 후보입니다. **가장 안정적인 방식이라고 확정한 것은 아닙니다.** 비교 프로젝트의 쿠키 복사·외부 인증 저장 문제는 해당 구현을 그대로 채택하지 않는 근거이며, 공급자 페이지 안에서만 인증을 처리하는 same-origin 직접 HTTP 또는 hybrid 방식 전체를 배제하는 근거가 아닙니다. 이 대안은 구현·실계정 비교 전입니다. SDK도 private Angular/Rx 구조에 상당히 결합돼 있어 변경 대응 비용이 있습니다.

직접 HTTP/hybrid를 비교하려면 정상 보호를 거친 최종 요청과 지원되는 직렬화·수신 의미가 같다는 source 근거, 해당 페이지의 브라우저 인증 범위, 물리적인 한 번 생성, 정확한 요청/CID/선택 candidate/final/history 소유권과 전체 공유 계약을 먼저 입증해야 합니다. 독립 fetch는 SDK의 retry machinery에 들어가지 않을 수 있으므로 SDK 내부 재연결 위험만으로 이를 불가능하다고 단정하지 않습니다. 보호를 생략·추론하거나 인증을 도구로 읽는 실험, 모호한 기존 요청의 재전송은 하지 않습니다. 현재 고정 SDK 수신 시험은 이 대안의 실패나 제품 전체의 최적 선택을 증명하지 않습니다.

독립 source 재검토에서 genuine Vvc 준비 함수와 정확한 Ixa stream의 projection 전 수신 경로를 찾았습니다. 전자는 page-owned HTTP 준비의 구체적인 후보이고, 후자는 현재 outbound 경로를 유지하며 조건부 UI marker 의존성을 줄이는 후보입니다. Vvc/HTTP는 아직 구현·실행 전입니다. Raw stream 경로는 구현과 합성 검사를 마쳤지만 actual 답변/history를 수용하지 못했으며 현재 초기 owner-view 연결을 확인 중입니다. 정확한 source 경계와 아직 입증하지 못한 계약은 [전송 조사](background-web-transport.md#alternative-preparation-and-raw-stream-seams--source-only)가 소유합니다.
